# Systematic Debugging

**No fix without a root cause you can state in one sentence and defend with evidence.** A fix
for a cause you have not identified cannot be verified, so you will not know whether it worked —
it only moves the symptom.

This skill owns **finding out why**. Slowness is a different question (`performance-engineering`);
so is what the test should assert once you know (`testing`).

## Contract

```
§CAUSE    ¬fix ∅root-cause-stated-in-1-sentence ∧ evidence
§OBSERVE  read FIRST error ¬last · verify-assumption ∀evidence ¬belief
§ONE      1 hypothesis · 1 variable · 1 change per experiment
§HALVE    ∀experiment ⇒ halve the search space (bisect)
§GATE     3 failed-fixes ⇒ STOP · re-derive · ⍰user ¬attempt-4
§BAN      guess-fix ∅reproduction · null-check-to-silence ·
          batch-multiple-changes · blame-compiler ∅minimal-case
```

## The loop

### 1. Reproduce

Get a deterministic reproduction, or **measure the failure rate** if it is flaky — "3 in 50 runs"
is data; "sometimes" is not. Capture the exact error, environment, inputs, and versions.

Read the failing code path and the actual data before theorizing. Reasoning from memory of how
the code "probably" works produces hypotheses about a program that does not exist.

If you cannot reproduce, gather more facts — logs, state diffs, timing. **Do not guess-fix.** A
fix for an unreproduced bug cannot be verified, so you will not know whether it worked.

### 2. Observe before theorizing

**Read the first error, not the last.** Downstream errors are noise generated by the first one.

Read the actual code path and the actual data. Verify every assumption with evidence — logs,
debugger, breakpoints, print probes. "Is this function even called?" is a question with an
observable answer, and the answer is surprising often enough to always ask.

### 3. Hypothesize — falsifiable, one at a time

State it as "X causes Y because Z", with a prediction the next experiment could **refute**. A
hypothesis nothing could disprove is not a hypothesis.

Prefer the cheapest experiment that can kill it. Killing a hypothesis fast is progress.

### 4. Experiment — one variable at a time

- **Minimize the reproduction**: the smallest input or code slice that still fails. This alone
  often reveals the cause.
- **Bisect**: by commit (`git bisect`), by data (halve the input), by code path (disable half).
  Each step halves the search space — that is what makes it converge.
- **Change one thing per run** and revert experimental changes afterward. Two changes at once and
  you can no longer attribute the result.

### 5. Root cause → minimal fix

State the root cause in one sentence. **If you cannot, go back to step 2** — you are not done
diagnosing, whatever the code is doing now.

Fix the cause, not the symptom. The fix must make the original reproduction pass, and you must be
able to explain *why* it does.

Fix only the root cause you found. A nearby pre-existing bug or improvement goes in the report as
a follow-up, not in the same change — mixing it in makes the fix harder to verify and to review.

### 6. Lock it in

- Add a regression test that **fails without the fix and passes with it**. Verify both directions;
  a test that passes before the fix is testing nothing.
- Run the full suite for collateral damage.
- Note the cause, the fix, and why it cannot silently regress.

## Escalation gate

**After three failed fix attempts: stop.** The mental model is wrong somewhere, and attempt four
will be wrong in the same way.

Re-derive from scratch. Write down explicitly what is **proven** versus what is **assumed** — the
bug is almost always hiding in something assumed. Then question the architecture with the user
rather than making another attempt.

## Flaky-failure playbook

Suspects, in the order they usually turn out to be true:

1. Shared mutable state between tests
2. Time or clock dependence
3. Async ordering and races
4. Network or filesystem nondeterminism
5. Test-order dependence — compare running isolated versus in the suite
6. Hidden randomness — seed it and see if it becomes deterministic

**Flakiness is the bug, not a nuisance around it.** A test that fails 2% of the time is reporting
a real race that will eventually happen in production.

## Rationalizations that hide bugs

| If you think… | Reality |
|---|---|
| "Adding this null-check or try/catch makes it go away" | You hid the symptom; the corruption is still upstream |
| "It's probably the framework or compiler" | It almost never is. Prove it with a minimal case first |
| "It works on my machine / the re-run passed" | Flakiness **is** the bug: race, ordering, time, or shared state |
| "Too urgent for a regression test" | The same bug returning mid-incident is slower than writing it |
| "Multiple changes at once saves time" | You lost the ability to attribute the result — that is lost information, not saved time |

## Boundaries

| Need | Skill |
|---|---|
| Writing the regression test, test design | `testing` |
| Slowness rather than wrongness | `performance-engineering` |
| Memory corruption, UAF, sanitizer selection | `memory-safety` |
| Build, run, simulator loops, on-device reproduction | `xcode` |
| Concurrency semantics behind a race | `swift` |
| Whether the fix is reviewable and complete | `code-review` |
| Running the suite or a long reproduction, and waiting on it | `work run` (`planner`'s `scripts/work.py`), `engineering-practices` §6 |
